# История изменений

*Читать на [английском](CHANGELOG.md).*

Все заметные изменения VD Infos. Даты в формате ISO (ГГГГ-ММ-ДД).

Ветка 2.x — полная переработка; последний публичный релиз ветки 1.x — [v1.11-beta6](https://github.com/VD171/VD-Infos/releases/tag/v1.11-beta6) (2024-12-02). Всё между ним и 2.00 — та самая переработка, описанная ниже.

## [Не выпущено]

## [2.24] - 2026-10-08

- **Отмечается расходящееся чтение, а не только проверка.** Раньше каждая карточка несла один значок вердикта на всю проверку; теперь каждое чтение, значение которого не совпадает с эталоном проверки, помечается красным (`JVM`, `JNI 92B`, `TEE` ...), поэтому метод, в который проник хук, виден без чтения значений. Пометки берутся из собственного сравнения вердикта — наличие, сопоставимые чтения, одинаковая нормализация, одинаковая полярность булевых слов, — поэтому они не могут расходиться.

- **Новая настройка: эталонная линза.** `Reference lens` в меню переполнения определяет, относительно чего отмеряются пометки: `Majority (auto)`, значение по умолчанию, сохраняет наиболее повторяющееся чтение каждой проверки как базовое, либо выбирается одна линза (`JVM`, `JNI`, `JVM+SH`, `JNI+SH`, `TEE`). На устройстве, где один путь чтения, как известно, возвращается неподменённым — скажем, `getprop` в отдельном процессе, — его выбор делает помеченными подменённые пути вместо реального чтения. Проверка, которая не читает через выбранную линзу, возвращается к большинству. Выбор сохраняется и фиксируется в отчёте о расхождениях.

- **Экспортируемый отчёт помечает расхождения.** Каждое расходящееся чтение в `vdinfos-report.json` теперь несёт `"mark_before": ">>> DIVERGENT >>>"` перед своим значением, `"mark_after": "<<< DIVERGENT <<<"` после него и `"divergent": true`; у совпадающих чтений эти поля отсутствуют, поэтому `grep mark_before` попадает точно на расхождения, а `"divergent": true` доступно для скриптов. Снимок внутри приложения и его кеш остаются необработанными — пометки есть только в экспортируемой копии.

- **Новый экспорт: только расхождения.** `Save divergences` и `Share divergences` записывают `vdinfos-divergences.json` с одной записью на каждую расходящуюся проверку (`probe`, `title`, `category`, `verdict`), содержащей только проблемные чтения, вместо всего отчёта примерно на 4500 чтений.

- **Категории теперь свёрнуты.** Заголовок категории больше не раскрывается сам из-за наличия несовпадений; их число уже говорит о том, что внутри. Поиск или фильтр, оставляющий одну категорию, по-прежнему раскрывает её.

- **Новый фильтр представления: только расхождения и эталон.** Переключатель в меню переполнения показывает лишь проверки с расходящимся чтением и внутри карточки оставляет только расходящиеся чтения плюс эталонное чтение, с которым они сравнивались.


## [2.23] - 2026-10-08

- **Заголовок — одна компактная строка, и он больше не борется со списком проверок.** Панель заголовка высотой 64dp, чей заголовок переносился на вторую строку («VD Infos» с версией под ним), заменена одной строкой — название, версия и слоган 9sp, — высота которой следует за содержимым. На узком экране или при крупном системном масштабе шрифта заголовок обрезался и наезжал на список; теперь он остаётся целым, а список начинается сразу под фильтрами. Вернулось около 100dp вертикального пространства.

- **Четыре действия заголовка переехали в меню переполнения.** Раскрытие идентичности, сохранение в файл, отправка отчёта и «О программе» — те же действия за одной кнопкой «⋮» вместо четырёх значков размером 48dp, что вернуло заголовку около 160dp панели.

- **Поле поиска — тонкая строка 34dp без лупы.** Обычное поле (моноширинный шрифт 12sp, контур 1dp, основной цвет при фокусе) заменяет `OutlinedTextField` размером 56dp, а кнопка очистки «✕» появляется только тогда, когда есть что очищать.

- **Легенда вердиктов убрана.** Цветные точки с «divergent / match / single / info» висели под сводкой и занимали пятую часть экрана; каждая карточка по-прежнему несёт собственный цветной значок вердикта, поэтому соответствие остаётся видимым там, где это важно.

- **Отступы сводки и фильтров уменьшены.** Счётчик расхождений уменьшается с `titleLarge` до `titleMedium`, отступы блока — с 16/8dp до 12/1dp, а ряд чипов — с 8dp до 4dp.


## [2.22] - 2026-10-01

- **Новая проверка: самопроверка FLAG_SECURE.** `integrity:flagsecure_honored` устанавливает `FLAG_SECURE` на собственном окне приложения, читает его обратно, затем сбрасывает. Хук снятия блокировки скриншотов на `Window.addFlags`/`setFlags` отбрасывает бит, поэтому флаг, считанный обратно как отсутствующий (`STRIPPED`), и есть признак. Вариант на стороне композитора SurfaceFlinger оставляет флаг окна установленным и здесь не рассматривается.

- **Аттестация EC против RSA разделена на три проверки.** Старая единственная карточка `attest:keybox_ec_vs_rsa` заменена тремя, каждая со своим вердиктом:
  - `attest:rot_ec_vs_rsa` — сравнивает корень доверия (состояние проверенной загрузки, блокировка устройства, ключ загрузки, root), считанный через запрос EC и через запрос RSA; расхождение означает, что путь RSA не покрыт keybox. Уровень безопасности не голосуется (ключ EC запрошен через StrongBox, ключ RSA — нет).
  - `attest:leaf_sig_alg` — признак keybox только с EC, подделавшего путь RSA своим ключом EC, — листовой сертификат аттестации RSA, подписанный ECDSA вместо RSA.
  - `attest:batch_key_ec_vs_rsa` — цепочки EC и RSA должны быть подписаны разными ключами аттестации; общий подписант (серийный номер сертификата или открытый ключ) — признак «только EC», а расходящийся serialNumber субъекта (идентичность устройства) — отдельный признак. Общее имя (common name) не сравнивается. Серийный номер и идентичность показываются как отпечатки SHA-256, необработанные значения — за кнопкой с глазом и вне экспортируемого JSON, как в `attest:sb_tee_signer`.

- **Новая проверка: согласованность подмены типа сети.** `net:nettype_consistency` сравнивает транспорт, о котором сообщает фреймворк (`hasTransport`), с именем активного интерфейса (`LinkProperties.getInterfaceName`) и состоянием wlan из sysfs. «mobile» поверх интерфейса `wlan` и есть подмена.

- **Новая проверка: уровень аттестации StrongBox.** `attest:strongbox_level` запрашивает ключ на базе StrongBox (там, где эта возможность присутствует) и проверяет `attestationSecurityLevel`. Результат уровня TEE или отсутствие аттестации StrongBox — признак keybox уровня TEE, выдающего себя за StrongBox. Дополняет `attest:sb_tee_signer`; неприменимо без возможности StrongBox.

- **`prop:variants:*` больше не помечает законные ребрендинги и GSI как расщепление.** Суббренды, поставляющие системный образ другого бренда (POCO/Redmi на Xiaomi, OnePlus/oplus/OPPO/realme), и GSI (`generic_system_google`) читались как межраздельные расхождения. Разделы, помеченные как generic, теперь исключаются из голосования, а значения канонизируются через `assets/data/prop_identity_groups.txt` перед сравнением; необъяснённое расщепление по-прежнему становится красным. Матрица по-прежнему показывает необработанные значения по разделам.

- **Сломанный shell `pm` больше не читается как расхождение по числу пакетов.** Когда `pm` без root даёт сбой (`Failure calling service package`), проверки подсчёта совпадали с текстом ошибки по нестрогому шаблону `*package:*` и сообщали `0`, расходясь с реальным `getInstalledPackages()`. Теперь они считают только строки `^package:`, а сбой трактуют как недоступность (исключается из голосования), а не как `0`. Исправляет частую ложную тревогу на сильно изменённых и бюджетных ROM.

- **`hw:cpu_cores` сравнивает общее число с общим.** Он голосовал за количество онлайн-ядер (`availableProcessors`, `_SC_NPROCESSORS_ONLN`, которое падает, когда ядро паркует ядра) против общего (`present`), поэтому устройство big.LITTLE с припаркованными ядрами давало расхождение. Теперь голосование учитывает только общее (`_SC_NPROCESSORS_CONF`, `present`); значения онлайн-ядер остаются как эталонные строки.

- **Примечание к проверке переехало в диалог информации.** Лампочка открывается для любой проверки с примечанием или исправлением (раньше — только с исправлением), показывая сначала примечание, а ниже исправление; под карточкой ничего не висит.

- **Карточка подписанта StrongBox/TEE не несёт примечания.** Вердикт «общий или различный» и два отпечатка говорят сами за себя; у отпечатка остаётся кнопка с глазом для раскрытия серийного номера.

- **`attest:sb_tee_signer` включается только при наличии возможности StrongBox.** Устройство без StrongBox больше не сравнивает подписанта TEE с отсутствующим (ложное расхождение) и сообщает о неприменимости; там, где возможность есть, но аттестация StrongBox не выдаётся, выводится `STRONGBOX_MISSING`.

- **Новая проверка: барьер чтения ограниченной настройки.** `integrity:settings_read_gate` читает ключ, который Android 12+ скрывает от приложений с target SDK 31+. Она выполняется только когда и устройство, и target приложения — 31+ (поэтому сборка совместимости с SDK 27 неприменима, а не расходится); там ненулевое значение — признак скрывающего слоя, отвечающего раньше проверки чтения платформы.


## [2.21] - 2026-09-28

- **Детализация подписанта StrongBox/TEE теперь по умолчанию показывает отпечаток.** `attest:sb_tee_signer` сообщает «общий или различный», как и раньше; эталонная строка теперь показывает 16-символьный hex-отпечаток SHA-256 каждого серийного номера (одинаковые серийные номера дают одинаковый отпечаток), с кнопкой с глазом для оригинала, а необработанный серийный номер не попадает в экспортируемый JSON.

- **Идентичность ядра сверяется между системным вызовом, sysctl и свойством.** `kernel:version_claim` сравнивает `ro.kernel.version` с реальным релизом `uname(2)` (свойство, подменённое поверх другого ядра, даёт расхождение). `kernel:release` добавляет `/proc/sys/kernel/osrelease` и `/proc/version`; новый `kernel:version_string` сверяет строку `#N SMP ...` между `uname(2)`, `uname -v`, `/proc/sys/kernel/version` и `/proc/version`. `kernel:selfbuild` показывает происхождение сборки из `/proc/version` (сборщик, компилятор, идентификатор сборки). Новые `kernel:build_date` (ядро собрано заметно позже ROM), `kernel:config` (KSU/SUSFS, локальная версия в `/proc/config.gz`) и `kernel:modules` (ksu/susfs/magisk в `/sys/module` и `/proc/kallsyms`). Линзы на основе файлов аккуратно бездействуют там, где песочница им отказывает.

- **Пять новых проверок по всем приложениям.** `pkg:xposed_scan` помечает установленные пакеты, несущие метаданные манифеста Xposed (`xposedmodule` и т. д.). `pkg:debuggable_scan` перечисляет приложения с `FLAG_DEBUGGABLE`/`FLAG_TEST_ONLY`. `pkg:uid_groups` помечает пользовательское приложение, разделяющее Linux UID с системным. `pkg:updated_system` перечисляет пакеты с `FLAG_UPDATED_SYSTEM_APP` (установка в обход магазина заменила системное приложение). `isrc:landscape` группирует видимые приложения по записанному установщику.

- **Аттестация ключей читается тремя способами и сверяется.** Аттестации из свойств устройства, обычного TEE и (где доступно) StrongBox выстраиваются по полям RootOfTrust и уровней патча (хеш/ключ/состояние проверенной загрузки, блокировка устройства, патчи); подлинное устройство возвращает один и тот же RootOfTrust для любого режима, поэтому отличающийся по режиму даёт расхождение. Каждое поле голосует по свойствам устройства, обычной аттестации, второй случайной задаче и аттестации RSA (StrongBox для справки). `attest:challenge_echo` проверяет, что аттестация повторяет свежую случайную задачу (переигранный keybox не проходит). Аттестованный серийный номер присоединяется к сверке идентификаторов устройства.

- **Более чистые метки линз для аттестации и native-вариантов.** `JNI 92B`, `TEE Plain`, `TEE StrongBox`, `TEE RSA`, `TEE Alt` показываются собственным чипом вместо суффикса имени метода.

- **Живая идентичность GPU вернулась и читается двумя способами.** `gpu:vendor/renderer/version/glsl` читают `glGetString` через внеэкранный контекст EGL посредством линзы JVM и native-линзы EGL (плюс GLES из `ActivityManager` для справки), поэтому хук `glGetString` на стороне Java даёт расхождение. Строка рендерера, выдающая эмулятор (SwiftShader и т. п.), снова видна.

- **Больше полей идентичности телефонии.** Type Allocation Code (сверяется с первыми восемью цифрами IMEI), код производителя, id / имя оператора SIM / id конкретного оператора, а также пакет визуальной голосовой почты теперь входят в поверхность телефонии.

- **Две проверки покрытия, перенесённые из 1.x.** `integrity:keychain_blacklist` читает mtime/размер `/data/misc/keychain/pubkey_blacklist.txt` тремя способами (установка сертификата перезаписывает его). `integrity:buildprop_vs_runtime` помечает ключ, значение которого во время выполнения было изменено через `resetprop` и разошлось с `build.prop` на диске.

- **Новые ключи свойств в каталоге.** `ril.rfcal_date`, `ril.manufacturedate`, `ro.product.nickname` (в разделе Device), `persist.sys.exif.model` (в разделе Model).

- **Сверка счётчика загрузок теперь направленная.** `Phenotype_boot_count` (сервисы Play) законно отстаёт от `boot_count`, когда GMS пропускает фиксацию загрузки, поэтому срабатывает только невозможное направление — снимок впереди `boot_count` (сброс). Обнуление `boot_count` для имитации нового устройства по-прежнему ловится; отставание больше не даёт ложных срабатываний.

- **Повторяющиеся свойства по разделам сверяются по линии происхождения.** `prop:variants:*` читает каждый вариант раздела, который предоставляет устройство (разделы в `assets/data/partitions.txt`, поля и область — в `prop_families.txt`): поля идентичности (бренд, производитель, устройство, теги, тип) должны совпадать по всем разделам, поля линии происхождения (отпечаток, модель, идентификатор сборки, даты, версии) — в пределах каждой линии (system/vendor/product/bootimage), поэтому устройство с GRF и разными версиями Android в system/vendor читается чисто, а частичное изменение отпечатка раскалывает линию. Показывает полную матрицу. `prop:enum_vs_getprop` сравнивает нативное перечисление свойств (`__system_property_foreach`) с `getprop` из другого процесса. Обнаружение разделов динамическое.

- **`integrity:buildprop_vs_runtime` читает реальные пути по разделам.** Он проверял `/system_ext/build.prop` и `/product/build.prop`, которые многие устройства держат в `.../etc/`; теперь пути берутся из `partitions.txt` и охватывают каждый раздел, включая `system_dlkm`/`vendor_dlkm`.

- **Покрытие сверено со сборкой Java из 1.x.** Четырнадцать потерянных ключей свойств вернулись в каталог (`gsm.version.ril-impl`, `ro.baseband.arch`, `ro.hardware.chipname`, `persist.graphics.egl`, свойства даты изготовления от OEM, `sys.kernel.firstboot`, ...), а её пакеты замаскированных скрывателей (`com.google.android.hmal`, `com.tsng.dyhhvf`, Android Faker) пополнили списки обнаружения.

- **Три вердикта с точки зрения приложения.** `integrity:ime_verdict` помечает несистемную клавиатуру, установленную в обход белого списка магазина. `integrity:store_authenticity` проверяет, что Play Store/GMS/GSF несут подписывающий сертификат Google (`known_certs.txt`); другой ключ — подделка/microG/перепаковка. `integrity:devgate` помечает настройку, доступную только разработчику (`dev_gated_settings.txt`), оставленную не по умолчанию при `development_settings_enabled=0`; каждая показывает своё значение по умолчанию в AOSP (`adb_allowed_connection_time` по умолчанию `604800000`).

- **`/data/local/tmp` перечисляется, а не только проверяется по имени.** `integrity:local_tmp_list` выполняет `getdents64` и показывает любую запись, доступную приложению, включая сброшенные модулем файлы. Заблокированное устройство оставляет каталог нечитаемым (EACCES — чистый ответ); видимая запись означает, что остатки доступны приложению.

- **Расхождения подтверждаются вторым чтением.** При `MISMATCH` движок один раз перемеряет и сообщает устоявшееся чтение только если расхождение не воспроизводится — он никогда не понижает вердикт у того, что сохранилось, поэтому реальное обнаружение никогда не скрывается, устраняется лишь мерцание (гоночная линза provider/binder). Кешированные проверки (аттестация, GPU) не затрагиваются.

- **Исправлено: фантом `call(GET_<store>)` у `content://settings`, подделывавший расхождения идентификаторов.** На некоторых устройствах (ColorOS/OnePlus) `call("GET_global", key)` периодически возвращал фантомный `"0"` для ключа из другого пространства имён, из-за чего `id:android_id`, `id:ads`, обход `spoof:*` и некоторые `set:*` мерцали красным и зелёным. Теперь читатель вызовов отбрасывает одиночный `"0"`, когда в другом хранилище есть реальное значение, сохраняя подлинный `"0"` (adb_enabled и т. п.) нетронутым.

- **Новое: сверка подписанта StrongBox и TEE.** `attest:sb_tee_signer` создаёт ключ на каждом уровне и помечает общий подписывающий сертификат, то есть один keybox (TrickyStore), подделывающий оба. Работает офлайн; сетевая проверка отзыва keybox исключена, чтобы VD Infos оставался без сетевого доступа.

- **Новое: классификатор инъекций по исполняемым отображениям и поиск скрытого суперблока.** `integrity:maps_exec` помечает исполняемое отображение `(deleted)`/`memfd`/`ashmem` только если оно RWX или начинается с сигнатуры ELF, поэтому реальный отвязанный `.so` ловится, а трамплин JIT в ART безвреден. `integrity:anon_minor` находит суперблок, скрытый в приватном пространстве имён (minor анонимного блочного устройства присутствует через `stat()`, но отсутствует в mountinfo), игнорируя долговременные изменения.

- **Новое: поиск модулей загрузчика, переживающий очистку maps.** `integrity:dlphdr` перечисляет модули через `dl_iterate_phdr` (загрузчик), а не через `/proc/self/maps`, поэтому хук, вычищающий свою запись в maps (Shamiko и т. п.), всё равно попадает в список; имена читаются безопасно от сбоев, страница за страницей, поэтому вычищенная строка не может вызвать SIGSEGV при проверке. `integrity:frida_port` помечает открытый `127.0.0.1:27042/27043` (классический сервер/гаджет Frida).

- **Новое: ловит скрыватель приложений, который только чистит список пакетов.** `integrity:concealment` берёт редактируемый сообществом список целей (`assets/data/conceal_targets.txt`) и для каждой цели, отсутствующей в `getInstalledPackages`, пробует двери, которые забывает частичный скрыватель: `getPackageInfo`, `getApplicationInfo`, `createPackageContext` (+ его APK как `ZipFile`), intent запуска и intent `MAIN`. Цель, скрытая из списка, но всё ещё достижимая через любую из них, и есть утечка; тогда выводится матрица дверей `L/P/A/C/Z/I/R` по каждой цели и карточка становится красной. Скрыватель, закрывающий все двери, читается чисто.

- **Подписывающие сертификаты теперь сообщают, чьи они.** Редактируемый сообществом каталог `assets/data/known_certs.txt` (`SHA-256<tab>owner`) помечает известный сертификат везде, где приложение его выводит (сверка установщика, разрыв подписи инициатора, дайджесты подписи, собственная подпись этого приложения). Поставляется с ключами Google, Motorola, Xiaomi (`CN=MIUI`), Telegram, Indus Appstore и VD171.

- **Проверка сертификата установщика называет установщик.** Обе линзы `isrc:self_initiator_sig` выводят инициирующий пакет рядом с хешем (`com.miui.packageinstaller: c9009d01… [Xiaomi, CN=MIUI]`), а примечание перечисляет причины; вердикт не меняется. Наблюдалось на Xiaomi.eu HyperOS 3: `getPackageInfo()` сообщает сертификат Xiaomi для установщика, тогда как запись об установке содержит другой (`f87bd41b…`) — этот ROM переподписывает систему, поэтому два API действительно расходятся, и расхождение остаётся.

Он сообщает о согласии между линзами, а не о чистом устройстве: хук, согласованно переписывающий каждый маршрут, читается так же.

  через popen без JVM. Две функции libc — это разный код с
  разными контрактами, а два shell-маршрута перехватываются по-разному, поэтому
  фреймворк, который переписывает один и не переписывает остальные, проявляется как расхождение.
  Сначала это ограничили «чувствительными» свойствами, чтобы сэкономить форки, и это было
  неверно дважды: `sensitive` означает «маскировать в интерфейсе», а не «подменяющему важно», так что
  `ro.build.fingerprint` и `ro.boot.verifiedbootstate` — два самых переписываемых
  свойства на устройстве — получили на один маршрут МЕНЬШЕ, чем неустановленное свойство IMEI. И
  форк — не дорогая часть: popen даёт в среднем 0,27 с на чтение против 0,47 с для
  маршрута через JVM, так что нормировали как раз более дешёвый маршрут. Полное сканирование —
  3002 чтения за 28 секунд.
- **Shell-команды выполнялись только через JVM — единственное место, где живёт хук.**
  `ProcessBuilder`/`Runtime.exec` — среди самых перехватываемых поверхностей на Android:
  фреймворк, скрывающий root от приложения, переписывает их там, в Java. Спрашивать только через
  этот маршрут — значит спрашивать ровно там, где говорится ложь. Добавлен нативный маршрут —
  `popen()` из JNI, который делает fork и exec, вообще не касаясь перехваченного класса, —
  и двенадцать команд, где ложь окупилась бы, теперь выполняются двумя способами: пути
  артефактов root, бинарник `su`, `which su`, grep внедрённой библиотеки по
  `/proc/self/maps`, маркеры монтирования, контекст SELinux, TracerPid и
  состояние проверенной загрузки. Расхождение между ними И ЕСТЬ хук. Измерено на обоих
  устройствах, включая одно с Magisk: они совпадают, а так и выглядит соответствие —
  и теперь это измерение, а не предположение.
- `grep` завершается с кодом 1, когда совпадений нет, поэтому процесс без внедрённых библиотек
  сообщал молчаливый null: отсутствие никогда не было указано. Теперь он говорит `absent`.
- Счётчик расхождений использует настоящий ресурс множественного числа вместо «(s)».
- **У команды `content` никогда ничего не спрашивали.** Поставщики читались только через
  Java ContentResolver; другого shell-маршрута в то же хранилище не
  было ни в одной проверке. Она всё же отвечает приложению — «Error while accessing provider»,
  потому что доходит до хранилища через `getContentProviderExternal`, которому нужны
  shell/root, — так что отказ теперь на экране как соответствующее чтение, а
  устройство, которое отвечает, и есть аномалия. Добавлено как ОДНА проверка соответствия плюс чтение
  Android ID: один `content query` стоит 2-3 секунды изнутри
  приложения, а объединение трёх хранилищ настроек срывало тайм-аут, показывая TIMEOUT 22
  раза и скрывая настоящий ответ. Поставщик `gservices` остаётся в стороне — команда
  не может до него добраться даже как root, это под силу только линзе Java.
- **Заполнитель — не ответ.** `Build.SERIAL` жёстко задан литералом
  «unknown» для любого приложения, нацеленного на O+, — фреймворк говорит «тебе это не дадут»,
  та же маскировка, что и у старого заполнителя `__system_property_get`. Прочитанный сырым, он
  противоречил `getSerial()`, который отказывает вслух, и проверка сообщала о
  расхождении там, где двое на самом деле СОГЛАСНЫ: приложению отказано в серийном номере. Оба
  теперь нормализуются в один токен отказа, поэтому соответствующее устройство совпадает и выделяется только
  устройство, которое выдаёт серийный номер. Намеренно ограничено этим одним чтением:
  `unknown` — подлинное содержимое `ro.bootloader` и `ro.carrier` на
  некоторых устройствах, где все три линзы с ним согласны, — нормализация по значению, а не
  по происхождению превратила бы 18 истинных чтений в ложные отказы.
- **Два ложных расхождения, которые могло показать только второе устройство.** Списки ABI
  объединялись через `", "` на стороне Java и через `","` в свойстве — форматирование,
  а не расхождение, и незаметное на устройстве с одним ABI. А `sys:selinux`
  смешивал два разных вопроса: `/sys/fs/selinux/enforce` — это текущее
  состояние, `ro.boot.selinux` — то, что сообщили загрузчику. Они выглядели
  сравнимыми только пока чтения файла были молча пустыми; как только отказ стал
  значением, `EACCES` начал «противоречить» значению `enforcing`, которое никогда не было тем же
  фактом. Свойство загрузки теперь контекст.
- **Проверки телефонии и собственного пакета перестали читаться только одним способом.** Свойства
  радио несут те же факты, которые сообщает TelephonyManager, поэтому оператор, MCC+MNC,
  код страны ISO, роуминг и число SIM сравниваются с ними через нативную
  и shell-линзу; состояние SIM, тип сети и базовую станцию показывают как контекст,
  потому что двое говорят о одном и том же разными словарями. эти
  свойства несут ОДНО ЗНАЧЕНИЕ НА СЛОТ SIM (`72423,`, `false,false`,
  `LOADED,NOT_READY`), а API отвечает для подписки по умолчанию, поэтому обе
  новые линзы берут первый слот — сравнение сырых значений пометило бы все десять.
  Имя собственного пакета этого приложения, uid и пакеты, разделяющие этот uid, теперь сравниваются
  с `/proc/<pid>/cmdline`, `getuid()`, `id -u` и `pm list packages --uid`.
- **Код возврата конвейера — это код последней команды, и это показывало ошибку как
  значение.** `cat /proc/N/cmdline | tr -d '\0'` завершается с кодом 0, когда `cat` падает, потому что `tr`
  отработал, а при объединённом stderr сообщение приходит выглядящим ровно как
  содержимое: приложение сообщило `cat: /proc/14101/cmdline: No such file or directory` как
  имя собственного пакета. ФОРМА ошибки shell (`cmd: subject: reason`) теперь
  распознаётся независимо от того, что заявляет код возврата.
- 46 заголовков телефонии и собственного пакета стали строковыми ресурсами; они ускользнули
  от более раннего прохода i18n, потому что идут через помощник, а не напрямую через
  конструкторы проверок.

- **Отказ — это чтение, везде.** Сбой из-за разрешений раньше попадал в
  корзину ERROR, что читается как «приложение сломалось» и оставляло интересный случай
  без ничего для сравнения: у устройства, которое ВСЁ ЖЕ выдаёт обычному приложению IMEI,
  не было расхождения, чтобы его показать. Сбои в форме отказа по разрешениям теперь становятся значением
  (`NOT_PERMITTED`, `EACCES`, `DENIED`, `EPERM`, `ENOENT`); настоящий дефект по-прежнему
  сообщается как ошибка. Шестнадцать проверок вышли из ERROR на тестовом устройстве —
  IMEI/IMSI/ICCID/MEID, информация о соте, номер линии, `/proc/version`, `/proc/stat`,
  `/sys/fs/selinux/*` и ключи ограниченных настроек, — и `Build.SERIAL` против
  `Build.getSerial()` обнаружился как настоящее расхождение: фреймворк отвечает
  `unknown` по одному пути и отказывает по другому.
- **Все три линзы теперь говорят на одном языке отказа.** Java сообщала `EACCES`, а
  нативная и shell-линза молчали об ОДНОМ И ТОМ ЖЕ запрещённом файле — это хуже любой
  из крайностей: выглядит как сравнение, но им не является. `/proc/version`,
  `/proc/stat`, `/sys/fs/selinux/enforce` и `policyvers` согласуются между всеми тремя.
- **Поля Build больше не читаются только одним способом.** Все 24 поля с каноническим
  системным свойством получили нативное и shell-чтение — константа `Build.*`
  инициализируется из свойства, поэтому свойство и есть второй, независимый способ
  прочитать то же самое, и именно пара ловит подмену, применённую к одной стороне.
- **Три shell-линзы были мертвы и ничего не сообщали.** `ls -d` по путям
  артефактов root завершается ненулевым кодом, как только ОДИН путь отсутствует, а это всегда так, поэтому
  shell-чтение артефактов root никогда ничего не выдавало (0 из 6 проверок);
  теперь оно отвечает `absent` — тем же словом, что использует нативная линза. `ip link` (0 из 4)
  и `getenforce` (0 из 1) отклоняются для недоверенного приложения и теперь показывают этот
  отказ вместо пустой ячейки.
- `settings get` показывается, но никогда не сравнивается: он доходит до поставщика через
  `getContentProviderExternal`, которому нужны shell/root, поэтому приложению отказывают каждый
  раз (измерено 22 из 22). Остаётся видимым, потому что устройство, которое там отвечает,
  выдало обычному приложению привилегию уровня shell.
- Число установленных приложений получило чтение `pm list packages`.

## [2.14]

- **Отказ — тоже ответ.** Поверхности, которые песочница призвана закрыть, теперь проверяются намеренно, потому что `EACCES` — это соответствующее норме чтение: устройство, которое вместо этого отдаёт содержимое, норме не соответствует, и это нужно увидеть. 19 элементов (eMMC CID/serial, идентичность UFS и SoC, `/proc/cmdline`, `/proc/stat`, `/proc/1/*`, `/dev/kmsg`, `/system/build.prop`) плюс 22 службы `dumpsys`. Чтобы отказ можно было сравнить, он должен быть значением, поэтому нативная линза получила отчёт об errno в стиле `__system_property` (`EACCES`/`ENOENT`/...), Java-линза нормализует исключение, а shell-линза подмешивает stderr и приводит его к тому же токену. `dumpsys` отказывает в двух формах, и обе нормализуются: `DENIED` (нет разрешения DUMP) и `NO_SERVICE` (servicemanager даже не показывает службу приложению).
- **Рекламный идентификатор теперь действительно читается.** Он был пустым, потому что читался из хранилищ настроек, где GAID не живёт: он приходит из привязанной службы Play Services. Реализовано заново через сырую binder-транзакцию, без зависимости от Play. Прочёсывается и всё семейство ключей (AAID, а также OAID/VAID китайского OEM-альянса и `pps_*` от Huawei) по всем трём хранилищам настроек.
- **Каждый элемент настроек теперь читается дважды** — через кэширующий API `Settings.*`, который переписывают фреймворки хуков, и через запрос ContentResolver, идущий напрямую в хранилище. Расхождение означает, что API врёт приложению.
- **Системные функции** сравниваются как следует: полный набор из `getSystemAvailableFeatures()` против `pm list features` (другой процесс спрашивает тот же PackageManager), при этом объявляющий `etc/permissions/*.xml` показан как контекст, поскольку он законно отличается. Плюс 12 элементов по отдельным функциям.
- **Свойства идентификаторов OEM и восстановленные ключи настроек**: 77 свойств идентификаторов OEM (Meizu, Oppo, OnePlus, Asus, TCT, Verizon и варианты IMEI/MEID/ICCID/serial/MAC) и 13 ключей настроек, которые потеряла переписанная версия, включая трио hidden-api-policy (признак вмешательства) и ключи доступности (служба доступности может читать экран). `READ_GSERVICES` и `AD_ID` объявлены: у обоих protectionLevel «normal», выдаётся при установке без запроса, так что то, что они открывают, полностью укладывается в то, что любое установленное приложение может о вас прочитать.
- **x86** добавлен в ABI (x86_64 уже был), так что приложение работает и на 32-битных эмуляторах.
- Исправлены три ложных расхождения, где две линзы отвечали на разные вопросы: маркеры монтирования (сводка против сырых строк mountinfo и «overlay» как нестрогая подстрока, тогда как OverlayFS обычен на Android), `which su` (обход PATH против одного жёстко заданного пути) и включённые методы ввода (отфильтрованное представление фреймворка против сырой настройки).
- **Четвёртое ложное расхождение, и худшее из них: приложение выдумывало root.** Проверка маркеров монтирования сканировала всю строку `/proc/self/mountinfo` на `ksu`, а каждая строка ext4 несёт опцию монтирования `journal_checksum`, которая содержит эту подстроку. Чистый Samsung сообщал о KernelSU. Теперь проверка читает только точку монтирования, тип файловой системы и источник, но никогда опции, в обеих линзах.
- **Название каждой проверки переводимо.** 172 названия были литералами в конструкторах проверок; теперь это строковые ресурсы, подставляемые во время сборки, так что экспортированный отчёт всё равно несёт читаемый текст.
- **GSF ID стучится в обе двери.** В Android 16 база `gservices` переехала из `com.google.android.gsf` в провайдер Play Services, поэтому старый authority отвечает пусто на устройстве, где идентификатор на самом деле есть. Опрашиваются оба.
- **Снимок и общий отчёт записываются атомарно.** UI-сканирование и фоновый воркер держали каждое своё хранилище и писали один и тот же файл в одно и то же время; каждый поток обрезает файл при открытии, но затем пишет с нуля независимо, поэтому более короткие данные оказывались внутри более длинных, а хвост более длинных оставался за их концом. В результате получался файл с полным JSON-объектом и мусором после него, что проявлялось только на устройстве, достаточно медленном для такого перекрытия. Теперь записи сериализованы, и каждая запись идёт через временный файл с переименованием на место.
- Исправлены два NPE по типу платформы (курсор GSF ID и перечисление сетевых интерфейсов — оба объявлены non-null в Kotlin и оба на практике nullable).
- **Поиск показывает то, что находит.** Совпадение внутри свёрнутого раздела оставалось скрытым; теперь разделы раскрываются, пока активен запрос. Плюс кнопка очистки в поле поиска и более крупная строка версии в шапке.

## [2.13]

- **Исправлено нативное чтение, которое могло выдать сообщение об ошибке libc как значение.** Нативная линза использовала `__system_property_get()`, буфер которой — 92 байта (`PROP_VALUE_MAX`). Для свойства длиннее этого bionic отказывается обрезать и записывает в буфер буквальную строку `Must use __system_property_read_callback() to read`. Этот заполнитель — сообщение об ошибке, а не значение: он показывался как нативное чтение и расходился с Java- и shell-чтениями — ложное несовпадение на любом устройстве с длинным свойством. Теперь нативная линза читает через `__system_property_find()` + `__system_property_read_callback()`, у которой нет ограничения по длине, и каждая метка обновлена так, чтобы называть фактически используемую функцию. Проверено на свойстве из 309 символов: все три линзы теперь возвращают его целиком.

## [2.12]

- **Диалог «О приложении» стал читаемым.** Он открывался плотным абзацем описания, а всё остальное было мелким шрифтом. Описание убрано, шрифт крупнее (строки и ссылки — body-large, заголовки разделов жирные), так что остаётся только то, что важно: проект, контакты и загрузка.

## [2.11]

- **Диалог «О приложении».** Кто написал приложение, где лежит исходный код, лицензия и контакты (Telegram, e-mail, XDA, GitHub) — в один тап в верхней панели. Переписывание 2.x это потеряло, так что информация была только в README.
- **Неожиданная ошибка теперь открывает диалог с возможностью копирования вместо того, чтобы убивать приложение.** Обработчик неперехваченных исключений пишет трассировку в приватные файлы приложения, приложение перезапускается, а следующий запуск показывает полную трассировку стека в прокручиваемом диалоге с кнопкой копирования, так что её можно вставить в отчёт. Защита не даёт сбою при запуске зациклить перезапуск. Ничего не передаётся: службы отчётов о сбоях нет, и у приложения нет разрешения INTERNET, так что отчёт покидает устройство только если вы сами его скопируете. Диалог также ведёт прямо к контактам, так что отчёт действительно можно куда-то отправить.
- Нативные чтения в элементах аттестации теперь называют свойство, которое читают (`__system_property_get ro.boot.verifiedbootstate` вместо голого `__system_property_get`), в соответствии с тем, как подписаны Java-чтения.

## [2.10]

- **Меньше ложных срабатываний на элементах идентичности.** Теперь вердикт сравнивает только чтения *одного и того же* поля. Каждое `Build.*` сравнивается со своим каноническим свойством (`ro.product.model`, `ro.build.fingerprint` ...) через Java/native/shell; варианты по разделам (`ro.product.vendor.*`, `.system.*`, `.odm.*`), которым Android намеренно позволяет различаться, остаются видимыми, но помечены как «контекст» и больше не вызывают MISMATCH. Тег TEE присоединяется к сравнению только когда следует тому же соглашению об именовании, что и `Build.*` (brand/device/manufacturer); для model/product он использует кодовое имя, поэтому показан только как контекст. Model, product и отпечаток снова MATCH, тогда как настоящий хук `Build.*` (расходящийся с каноническим свойством) по-прежнему ловится, а расхождение TEE security-patch остаётся красным.
- **Исправлено падение при раскрытии категории.** Свойство, присутствующее и в сыром каталоге, и в доменном модуле, который перекатегоризирует его (маркеры эмулятора, флаги целостности, DNS, GPU), давало две проверки с одним id; дубликат ключа ленивого списка ронял экран, как только отрисовывались обе, что первым проявилось в разделе «Эмулятор». Теперь реестр хранит одно чтение на id (доменное, которое несёт более осмысленную категорию).

## [2.09]

- **Глубже SELinux, методы ввода и нативное второе мнение.** Новые элементы сравнения, каждый по-прежнему читается несколькими методами: контекст SELinux (`/proc/self/attr/current` через Java, нативные open/read и `id -Z`), версия политики и флаг MLS, включённые и установленные методы ввода (IMM, Settings.Secure, `settings`/`ime`) и время загрузки (`/proc/stat btime`). TracerPid и маркеры монтирования (magisk/overlay/ksu) читаются один раз через JVM/File и ещё раз через нативные сырые `open()`/`read()`, так что хук `/proc`-файлов только на Java расходится с нативным чтением.
- **Больше поверхностей на элемент.** Serial теперь также читает `androidboot.serialno` из `/proc/cmdline`; MAC добавляет чтение `ip link` наряду с sysfs и нативным; источник установки добавляет `updateOwnerPackageName` (API 34).

## [2.08]

- Закрыт разрыв против Zygisk-спуферов в стиле COPG/PIF: `Build.VERSION.*` (release, SDK int, codename, incremental, security patch) и время сборки теперь сравниваются со своими свойствами `ro.build.version.*` / `ro.build.date.utc` (раньше метод был один), так что подмена этих полей через `SetStaticObjectField` становится видна.

## [2.07]

- **Линза TEE / аттестации.** Генерирует ключ KeyStore с аппаратной аттестацией и разбирает запись аттестации ключа (состояние проверенной загрузки, блокировка устройства, уровни патча, корень доверия и — когда поддерживается — brand/device/model из защищённого оборудования), помещая каждое рядом с чтением свойства/Build. Запись аттестации подписана TEE, поэтому спуфер, переписывающий Build.* и свойства, не может переписать её: любое несовпадение — сильный признак. Только офлайн (без сети).

## [2.06]

- **Хвостовые сборщики** перенесены для полного соответствия 1.x: самоинспекция «этого пакета» через PackageManager (uid, gids, установщик, источник установки, время установки и обновления, target SDK, состояние enabled/instant/suspended, ограниченные разрешения из белого списка, информация о модуле, собственные метаданные Xposed...) и перечисления разрешения интентов (`queryIntentActivities`/`Services`/`BroadcastReceivers`/`ContentProviders`, `resolveActivity`, `queryInstrumentation`), а также `/dev/ptmx` и `stat`. ~577 элементов.


## [2.05]

- **Массовые сборщики**: полный список установленных пакетов, подписи (digests) по каждому приложению и запущенные службы/процессы (последние два на современном Android возвращают только это приложение — само по себе информативно).
- В заголовке приложения версия теперь отображается динамически (из `BuildConfig`), поэтому она всегда совпадает со сборкой.
- **Пакет переименован** в `ru.vd171.vdinfos`.
- Раздел README «Что проверяет» теперь содержит полный охват (отдельный документ об охвате был включён в него и удалён).


## [2.04]

- Более широкая поверхность идентичности устройства и аппаратного обеспечения, каждое значение читается всеми методами: SubscriptionManager (мульти-SIM: iccid/number/carrier/mcc/mnc/country по каждой подписке), основной IMEI, serial пользователя, Android ID через secure-провайдер, информация о соте, камеры, системные функции и больше ключей Settings (wifi_mac, device_name, boot_count, adb_enabled, development_settings_enabled, data_roaming, http_proxy).


## [2.03]

- **Отладчик методов.** Переработан так, что каждый элемент информации читается через *все* методы, способные его прочитать (например, `Build.SERIAL` / `Build.getSerial()` / `SystemProperties` / `getprop` / native), и сравнивается рядом; каждое чтение показывает свой точный источник. Каждое системное свойство читается тремя способами (SystemProperties / native / getprop).
- **Широкий охват**: идентичность устройства, идентификаторы, поверхность TelephonyManager, сеть (MAC по интерфейсам, Wi-Fi, Bluetooth, DNS), ядро/процессы/система, аппаратное обеспечение (CPU/память/датчики/дисплей/GPU), Widevine DRM, пакеты, аккаунты, WebView и расширенные детекторы root/хуков/эмулятора.
- **UI** сгруппирован в сворачиваемые разделы по категориям со счётчиками, по умолчанию раскрытые там, где есть расхождение; результаты поступают по мере выполнения сканирования.
- **Движок** усилен: shell-линза не может застопорить сканирование (ограничение по времени, сначала kill, затем чтение), проверки выполняются в IO-диспетчере с таймаутом на каждую проверку, а результаты больше не теряются при переполнении буфера.


## [2.02]

- **Сохранение в файл** через Storage Access Framework: современный выбор документов, где выбирается папка и можно переименовать файл (имя только предлагается). Прежнее окно «Поделиться» остаётся отдельным действием.
- **Проверка политики захвата экрана** (категория *Security*): показывает `DevicePolicyManager.getScreenCaptureDisabled` — значение, которое обычно навязывают FLAG_SECURE / модули разблокировки скриншотов. Только Java-линза, поскольку нет native/syscall-аналога для перекрёстной проверки.
- Типографика: из всего дерева исходников удалены em/en-тире и добавлена защита, чтобы они не вернулись.
- Документация: старый GitHub README/LEIAME объединён с README версии 2.x (английский и pt-BR); списки сокрытия root и обнаружения root перенесены в отдельный каталог (`CATALOG.md`); обновлены разделы контактов и загрузки.


## [2.01]

- **Двуязычное приложение**: все строки, видимые пользователю, вынесены в ресурсы — английский по умолчанию (`values/`) плюс pt-BR (`values-pt/`); приложение следует языку устройства.
- **Двуязычная документация**: `README.md` (английский) и `README.pt.md`.
- **Лицензия**: GNU **AGPL-3.0-or-later** (была MIT). Копилефт с сетевой оговоркой — выбран, чтобы форки исследовательского инструмента и инструмента против обнаружения оставались открытыми.


## [2.00] - переписывание

Полное переписывание с нуля вокруг одной идеи: читать каждый факт дважды (Java SDK против native/JNI) и показывать расхождения. Расхождение означает вероятный хук (XPrivacyLua / Xposed) — это и был исходный сценарий использования 1.x.

### Добавлено
- **Двухлинзовая проверка.** Каждая проверка читается через Java SDK *и* через libc/системные вызовы посредством JNI; **вердикт** отмечает, где они расходятся.
- **Native-линза (JNI).** `__system_property_get`, `uname(2)`, прямой `open()/read()` для `/proc` и `/sys`, MAC по интерфейсам из `/sys/class/net`, `getuid`, `statvfs` и поиск артефактов root/хуков на основе `access()` — без shell-процесса.
- **Параллелизм.** ~380 проверок распределяются по корутинам с ограниченной конкурентностью и поступают в UI по мере завершения (раньше был один последовательный `AsyncTask`).
- **Фоновая задача.** Задание WorkManager повторяет сканирование по расписанию, сравнивает результат с предыдущим снимком и уведомляет, когда любое значение меняется между запусками.
- **Современный UI.** Jetpack Compose + Material 3, динамический цвет, тёмная/светлая тема, живой прогресс, поиск, фильтры по категориям, режим «только расхождения», маскирование PII и экспорт в JSON/текст.

### Изменено
- Kotlin + Compose заменяют Java + `ExpandableListView`.
- `minSdk` 21 -> 26, `targetSdk` 35, Gradle Kotlin DSL + version catalog.
- Каталог из ~360 свойств из 1.x сохранён как чистые данные.
- Убрана обфускация строк (lsparanoid): исходники должны оставаться читаемыми.
